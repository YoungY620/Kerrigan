# Kerrigan 指导文件

你正在使用 Kerrigan DAG 框架执行任务。本文档包含所有任务通用的原则和规范。请在开始工作前阅读。

根据当前任务涉及的类型，还需要阅读对应的场景指南（见末尾"场景指南"部分）。

---

## 执行工作流

拿到一个 ready 节点后，遵循以下流程：

1. **读取节点详情**：`kerrigan-storage get --task <task-id> --node <node-id>`
2. **读取所有前驱节点的 result_summary**：对每个 predecessor 执行 `get`，理解上游产出
3. **判断前驱信息是否充足**：
   - 充足 → 继续执行
   - 不足 → 用 failure_reason 说明缺什么信息，**不要在信息不足时硬做**
4. **执行任务**
5. **判断是否需要衍生工作**：
   - 发现了新的子任务 → 用 `add` 创建新节点
   - 不需要 → 继续
6. **回写结果**：用 `update` 写入 status + result_summary 或 failure_reason

## 任务分解原则

### 先做后分解

- **不要预测两步以外的计划。** 第一轮只做粗粒度分解（2-3 个高层节点），后续轮次根据执行结果决定是否继续细化。
- **先做再说，但小规模试探。** 不确定是否需要拆分时，先做一个最小范围的尝试，验证思路可行、复杂度可控。确保每步可及时回退，不会错得太远。发现复杂度超出预期时，立即停下来分解为子节点。
- **实践前先验证可行性。** 在全力实施之前，通过多个独立的交叉验证节点评估方案是否可行、依赖是否满足、假设是否成立。用最小成本排除不可行路径。
- **已有计划可以随时重构。** 发现分解方式不合理时，add 新节点、建立新依赖来调整路径。
- **不要过度提前细化。** 缺乏实践依据的规划只是猜测，猜错的代价是整棵子树作废。

### 粒度判断

- 一个节点应该是"一个 agent 在一次 session 中能合理完成的工作"
- description 超过 500 字还说不清楚 → 应该继续拆分
- 一行命令就能完成 → 粒度可能太细，考虑合并

### 依赖最小化

能并行就并行。只有当 B 确实需要 A 的输出才能开始时，才建立 A→B 依赖。

## 节点描述规范

### summary

一句话，动词开头，说清要做什么。

好：`分析 src/auth/ 目录下所有认证相关代码的调用关系`
差：`认证模块`

### description

自包含的任务说明。假设执行者对项目一无所知。必须包含：

- **目标**：这个节点要产出什么
- **上下文**：引用哪些前驱节点的结果（node ID）
- **范围**：操作哪些文件/目录/资源
- **约束**：不该做什么、边界在哪里
- **产出要求**：result_summary 中需要包含什么信息

## 结果反馈规范

### result_summary 结构

```text
## 执行摘要
[一句话结论]

## 关键产出
[具体改了什么文件 / 发现了什么 / 生成了什么——可验证的产出]

## 对后续节点的建议
[下游 agent 需要知道的信息]

## 已知限制与未完成事项
[必须如实披露：未覆盖的场景、暂时绕过的问题、跳过的测试、做出的妥协、已知但未修复的缺陷、TODO/FIXME。隐瞒比缺陷本身更有害——下游节点会基于错误假设工作]
```

### failure_reason 结构

```text
## 失败原因
[根因分类：上游输入不足 / 任务描述不清 / 执行能力不足 / 外部依赖问题]

## 已尝试的方法
[做了什么、走到哪一步、具体报错是什么]

## 建议的修复方向
[应该增加什么节点、修改什么依赖、补充什么信息]
```

---

## 透明披露

**不隐瞒任何已知问题。** 没有做的、暂时绕过的、跳过的测试、做出的妥协——全部如实写在 result_summary 的"已知限制"中。

- 跳过了某些测试用例 → 写明哪些、为什么跳过
- 绕过了某个错误 → 写明绕过方式和潜在风险
- 做了妥协 → 写明妥协原因和更好方案的方向
- 有 TODO / FIXME → 在 result_summary 中体现，不要只留在代码注释里

---

## 交叉验证

**不单独相信任何一个任务的结果。** 重要的判断必须有多角度的交叉验证。

在 DAG 层面：多个独立节点对同一问题做出判断，由聚合节点比对结论。结论一致则可信；不一致则衍生进一步调查。

## 任务身份

框架不绑定固定角色，但每个节点有自己的类别。dispatch subagent 时，根据节点类别描述临时身份：

- 分析类：告诉 subagent "你是一个分析师，目标是..."
- 实现类：告诉 subagent "你是一个开发者，目标是..."
- 审查类：告诉 subagent "你是一个独立审查员，目标是找出问题..."

这是临时身份描述，不是固定角色分配。

## 错误处理

**什么时候 fail**：
- 前驱信息不足，无法合理执行
- 尝试后发现任务不可行
- 外部依赖不可用

**什么时候衍生新节点**：
- 执行中发现了原计划没考虑到的子任务
- 需要先做某个前置工作
- 主要工作完成但发现需要后续验证/清理

**不要做的**：
- 不要在 failure_reason 里写"我会继续尝试"——节点不会被重新执行
- 不要把多个不相关的工作塞进一个节点
